# Metacognition Plugin

## Starting context

Mason's answer to who the plugin is for, verbatim (2026-10-01):

> It's for everyone. It's not indsutry specific. Anyone who wants to dive deep into why they have the preferences they have in their field and codify them can use this.

Mason's framing of why the pipeline is open source, verbatim (2026-09-30):

> My metacognition skill, what's the harm in open sourcing that? A lot of the time I see people open sourcing their framework but not the results. For example, I open sourced BPE and I use it religiously, but I don't feel like someone could pick that up and displace me. For metacognition, it's just a skill building skill. It isn't even that unique it's a port of someone else's work.

## Project overview

Metacognition is a plugin for Claude that captures how one person judges work in a field they practice and turns that judgment into a skill Claude can apply.
It is a pipeline of five stages, each its own skill, so an extraction can be re-run from any point:

```
/metacognition:design      ->  <root>/<slug>/interview-spec.md   plan the interview; never asks a taste question
/metacognition:interview   ->  <root>/<slug>/archive.md          60 to 120 questions, answers kept verbatim
/metacognition:compile     ->  <root>/<slug>/profile.md          compress the archive; log every cut
/metacognition:calibrate   ->  <root>/<slug>/calibration/*.md    test the profile on real work; fold corrections back
/metacognition:skillify    ->  a new or augmented skill          package the calibrated profile
```

`<root>` is the extraction root, `./extractions` unless configured otherwise (Component D).
"The person" throughout this spec and the plugin means whoever's taste is being captured, which is the session user.

The plugin started as a private plugin in Mason's own marketplace.
This repo is now its only source: the framework is public, and the profiles and archives anyone produces with it stay theirs.
The first phase ports what exists on the private repo's `main` (commit `2806854`) and makes it work for any person on three surfaces: Claude Code, Cowork, and claude.ai chat.
Later phases bring over newer private edits and cut Mason's private marketplace over to consuming this repo.

The repo follows the layout Mason already runs in `team-gtm-skills`: a marketplace at the root, the installable plugin in a subdirectory, a `src/` source of truth that a sync tool copies into each self-contained skill, drift guards in pytest, a uniform version scheme (SemVer during the beta, CalVer once it reaches 1.0), and a release workflow that publishes the plugin zip.

How the surfaces differ, as documented at claude.com/docs/plugins/platform-support (read 2026-09-30) and confirmed by Mason's use of `team-gtm-skills`:

| | Claude Code | Cowork | claude.ai chat |
|---|---|---|---|
| Install | marketplace or `--plugin-dir` | marketplace or zip upload | marketplace or zip upload |
| Invoke | `/metacognition:<stage>` | `/metacognition:<stage>` | `/` plus the skill |
| Plugin agents | load | load | ignored |
| Shipped scripts | run on the user's machine | run in the session | run in the code execution sandbox, standard library only |
| Extraction files | the working directory | the working folder | the conversation's files; a pipeline can run in one long conversation, each stage using the files the last one wrote |

## Invariants

- Nothing private is committed: no real extraction, profile, or archive, no vault path, no private repo path, no model roster, and none of Ruben Hassid's prompt text. The only personal references are the author fields, the license, and the README credit line.
- This project never modifies the private repo (`claude-code-plugin-private`). The port reads private `main` at `2806854` through `git show`, never the working tree.
- `src/` is the single source of truth for shared references and scripts. The copies under `metacognition/skills/*/references/` and `metacognition/skills/*/scripts/` are generated by `tools/sync_skills.py` and never edited by hand.
- A skill reaches its own files by relative path (`references/profile-format.md`, `scripts/validate_artifacts.py`). `${CLAUDE_PLUGIN_ROOT}` and `../` paths never appear in a skill, because each skill must work alone in the claude.ai per-skill sandbox.
- Shipped scripts (`src/scripts/`) import only the Python standard library and run on Python 3.12 or newer (raised from 3.11 by issue #9, on the maintainer's ruling), because the claude.ai sandbox has no network to install packages. Dev tooling may have dependencies. A script a skill invokes lives in that skill's `scripts/` directory, synced from `src/scripts/`; `tools/` holds repo tooling that is never shipped and that no skill can reach.
- SKILL.md frontmatter carries exactly `name`, `version`, `description`, and `compatibility`. `description` is at most 1,024 characters and contains no angle-bracket token; `compatibility` is at most 500 characters.
- No model pins and no model guards anywhere: no `model:` frontmatter, no instruction to check or switch the session model. The person picks the model when they invoke.
- No working-directory guard. Every stage runs from any directory.
- No top-level `bin/` directory in the plugin; claude.ai and Cowork refuse to install a plugin that has one.
- Versions are uniform: every SKILL.md, `plugin.json`, `marketplace.json`, and `pyproject.toml` carry the same value. During beta the scheme is SemVer `0.x` (initial `0.1.0`); it flips to CalVer `YYYY.MM.DD` (with `.N` for a second release the same day) at the 1.0 maturity milestone. Versions move only on the maintainer's ruling.
- Pipeline rules that hold on every surface: one probe or one battery per turn (a battery is three to six closed verdict items in a single category; two open probes never share a turn, and a battery never mixes categories); a deferral to outside practice is researched in the same turn or recorded as open research, never banked silently; the interviewer never paraphrases at capture (dash and curly-quote codepoints are the one normalization); compile never resolves a tension and logs every cut; calibrate reads the profile and never the archive; every calibration artifact is labeled a probe that never ships; no stage starts the next one.
- Augment is the default whenever a skill already exists for the domain, and an augment never changes a SKILL.md without a diff the person has reviewed.
- Every setting has a default, and a missing config file is never an error. An unknown key or a wrong type in a config file is a loud error.
- Every example in a skill or reference is canonical; weaker models copy examples verbatim.
- Python: type hints everywhere, `ruff format`, `ruff check`, and `mypy --strict` clean, pytest for every script and tool, all run through `uv`. Test-first for anything under `src/scripts/` and `tools/`.
- Tests assert behavior, never the presence of a mechanism.
- GitHub Actions are pinned to commit SHAs.
- Git: work happens on feature branches through pull requests; only the maintainer merges to `main`.
- Writing: per .claude/rules/vendored/writing.md

## Goals

### Active Phase: Interview Retro

Done means a fresh interview run avoids the five failure modes the retro documents: an interview that is too reserved early, deferrals banked silently, floors that stop measuring coverage once batteries are used, four to five file edits per answer, and picker answers that mix the interviewer's words into the answer line.
Each of the retro's nine recommendations is implemented by a goal R1 to R9 below.
Goals R10 to R12 carry issues #9 and #10, which ship in the same phase.
Existing extractions stay valid: every format change is additive, and an archive written before this phase passes the validator unchanged.

#### R1: Turn Discipline and Batteries

- The interview loop's first rule becomes a turn discipline. A turn is one open probe, or one battery: three to six closed verdict items, all in one category, each answerable with a stance and a sentence. Two open probes never share a turn, and a battery never mixes categories.
- Open probes lead early, while the map of the person's judgment is forming, and whenever an answer needs laddering. Batteries take over once a category's shape is known and what remains is collecting verdicts. A battery item that gets a surprising answer earns an open follow-up.
- A request from the person for more concrete questions is a standing instruction for the rest of the interview, not a one-turn preference.
- Question seeds and forced-choice entries favor concrete scenarios over abstract framings, in design and in the interview.
- `battery` joins the probe types. Extraction theory rule 16's table gains two rows, the verdict battery and the evidence probe (R2), and the rule count stays sixteen.
- Design's own scope Q&A stays one question at a time. This goal changes the interview only.

#### R2: Live Research in the Interview

- When the person defers to outside practice ("look up what is standard") or asks for research, the interview researches in the same turn. It never banks a deferral for a later stage.
- Three-way fallback, the same as design's: dispatch the research agent where the surface loads plugin agents; otherwise run the same contract in-session with web access; with no web access, say so in one line, record the deferral under Open research as `unresolved`, and continue.
- When research returns, the interviewer presents the bottom lines with their sources, asks the person to ratify, adjust, or reject each, and logs the outcome as its own question entry with probe type `evidence`: the question line carries the findings and links, the answer line carries the person's reaction verbatim. A deferral that committed in advance ("whatever the standard is, do that") still gets presented and ratified.
- No cap on research rounds. Each 20-question progress note states the running count of research rounds.
- The research contract gains a second request shape, the practice lookup: input is one question about practice in the domain plus the person's stated lean, output is a short list of bottom lines, each with a source link, or the `no relevant results` line (Component G).
- Compile never writes a bare instruction to follow community practice. A ratified deferral compiles to the written practice with its citation; an `unresolved` one is listed in `<do_not_infer>` as not yet settled.

#### R3: Picker Use and Provenance

- Forced-choice probes, battery items the person answers by choosing, and research ratifications go through the host's choice picker when the surface has one. Open probes never do. With no picker, the same options are written as a lettered list in the turn.
- A picked answer logs the selected label verbatim and nothing else, followed by any words the person added, verbatim. Option description text is the interviewer's, so it is written into the question line as part of the option and never into the answer line.

#### R4: Floors Count Probes

- A category's `asked` count is a count of probes, not turns. An open probe, a forced choice, or an evidence entry counts one; a battery counts its number of items.
- `questions_asked` stays the count of `### Qnn` entries. The README's `interview n/floor` cell shows probes over the floor sum, may exceed the floor, and is marked complete when the archive's status flips.
- The interview spec format states the counting rule beside the category map, so design's floors and the interview's counters measure the same thing. Default floors do not change.

#### R5: Design Verifies Artifacts and Plans Register Coverage

- Before writing the artifact plan, design checks that each local path exists and holds real content. A missing path or an empty skeleton is recorded in the plan as unavailable, and the person is told at design time. Where the surface has no file access, design says it could not check.
- The category map gains a registers column naming which registers each category's questions target. A register that no category targets is a design-time error that design resolves with the person before writing the spec.
- The interview's progress note reports register coverage beside category coverage. A question with no register-specific content takes the domain's primary register, the first in `registers`. A register that surfaces mid-interview is raised with the person and, if accepted, added to the archive's `registers`.

#### R6: Exports

- The archive gains an optional `## Exports` section, kept up during the interview like the ledger. One line per redirect: `- E01 (Q92): <topic> -> <destination>`, where the destination is a skill the person named or `unassigned`.
- An export records taste the person voiced but assigned to a different skill's territory. Compile leaves export content out of the profile body and copies the list into `compile-log.md`. Skillify names the exports as follow-up work in its finish message and never writes them into the produced skill.

#### R7: The Append Script

- A fourth shipped script, `src/scripts/archive_append.py` (Component K), appends one entry and updates every counter in one call. The interview skill uses it in place of separate edits to the count, the category tally, the body, and the README cell.
- When the script cannot run, the skill makes one edit to `archive.md` that carries the body and the frontmatter counters together, then one edit to the README cell.

#### R8: Capture Conventions and Meta-Rule Routing

- Written into the interview skill and the archive format: when the person interrupts and dictates an answer again, the corrected dictation replaces the answer; a question the person did not understand is not logged, and the reframed question that got an answer is the entry of record; labels in the conversation may drift, and the archive's contiguous numbering is authoritative.
- Written into the compile skill: rules about how the person wants judgment exercised (when to reconsider a past decision, whose decisions outrank an adopted outside reference, removing before adding, how to raise a discouraged pattern, what posture to take where nothing is codified) are profile content. Compile places them in the existing sections; the seventeen profile sections and their order do not change.

#### R9: Fixtures, Evals, Docs, and Version

- A new synthetic fixture, `tests/fixtures/extractions/woodworking-battery`, exercises a battery, an evidence entry, an export, and an open-research line, and passes the validator. A new bad case, `extractions-bad/battery-item-mismatch`, fails with the battery finding only. The existing fixtures are not edited.
- The design and interview evals follow the changed skill text: an interview eval expects a battery once a category's shape is known and same-turn research on a deferral; a design eval expects an unavailable artifact to be reported and every register to be targeted. Evals stay out of the gate.
- Docs pages change with their sources in the same pull request: the interview, design, compile, and skillify stage pages, the `archive.md` and `interview-spec.md` format pages, and the Method page's rule 16 table.
- The phase ships as `0.2.0` in every version source, including `pyproject.toml`, `uv.lock`, and the README's beta notice.

#### R10: The Token Estimate Script (Issue #9)

- A fifth shipped script, `src/scripts/update_token_estimate.py` (Component L), recomputes a profile's `token_estimate` and rewrites the frontmatter field when it is stale. It replaces the inline `python3 -c` one-liner that compile prescribes and that calibrate needs after every fold-back.
- It ships in the compile and calibrate slices, because a skill can only run a script from its own `scripts/` directory. The repo's own gate calls the same file from `src/scripts/`.
- The compile skill's token-estimate step and the calibrate skill's fold-back step invoke it. The one-liner stays in both as the stated by-hand fallback for when the script cannot run.
- A pytest check runs it with `--check` over every committed good-fixture profile, so a fixture with a stale estimate fails CI.
- It and `archive_append.py` share conventions: `main(argv)` returning the exit code, exit 2 with one line naming the problem for a missing or malformed input, a write by temporary file and rename, and an underscore module name.

#### R11: Python 3.12 Floor (Issue #9)

- `requires-python` is `>=3.12`, ruff targets `py312`, and CI runs the gate on Python 3.12 and 3.13.
- Every statement of the floor moves with it: the script docstrings, the skills' "cannot run" fallback sentences, the references, the docs, and the surface checklist.
- The by-hand fallback covers a surface whose sandbox is older than 3.12. The surface checklist records the sandbox's Python version when the check is run.

#### R12: Skillify Grounded in the Provider Baseline (Issue #10)

- The README names the `plugin-dev` plugin as a highly recommended companion install and says skillify is the stage that uses it. It is never required: with it absent, every stage still runs.
- Before writing a scaffold or proposing a structure, skillify loads `plugin-dev:skill-development` through the Skill tool. When the plugin is not installed, or the surface cannot load another plugin's skill (claude.ai chat), skillify says so in one line, continues on its bundled scaffold conventions, and recommends the install in its finish message.
- The exemplar is an advanced option. With no `exemplar` setting, or one that names a path that does not exist, skillify skips the exemplar read silently. When an exemplar exists it may shape the output, and the baseline review still runs and is answered.
- Precedence, written into the skill: the person's decision, then the provider baseline review, then the exemplar, then the bundled templates.
- Augment mode assesses the existing target skill's structure before drafting any diff: description triggering, progressive disclosure, size, and reference layout, using the `plugin-dev:skill-reviewer` agent where it can be dispatched and the loaded baseline otherwise. When the structure holds, skillify says so in one line and continues on the diff path. When it does not, skillify presents the best alternative layout beside keep-as-is, with the findings as its reasoning, and the person decides before any diff is drafted.
- A restructure is applied only on the person's explicit choice. The assessment is a presented verdict, never an applied one.
- The skillify eval covers both augment verdict paths, structure holds and structure challenged, with a new fixture plugin whose skill is deliberately poorly structured.

#### G3: Shipped Scripts

Five standard-library modules under `src/scripts/`, each with a CLI and a pytest suite (Components C, D, E, K, L):

- `yaml_subset.py`: a strict parser for the YAML subset the artifact formats and config files use.
- `validate_artifacts.py`: the private `validate-artifacts.py` ported onto `yaml_subset`, same nine checks, same findings, same exit codes, with a 10,000-token ceiling (5,000 on private `main` at the port commit, raised by issue #3).
- `resolve_config.py`: the tiered settings resolver.
- `archive_append.py`: appends one interview entry and updates every counter in one call (goal R7).
- `update_token_estimate.py`: recomputes a profile's `token_estimate` and rewrites the field when stale (goal R10).

Skills invoke them as `python3 scripts/<name>.py`.
When a script cannot run (no code execution, or an interpreter older than 3.12), the skill applies the same rules by hand from its references and says so in one line.

#### G6: Fixtures and Evals

#### G7: Packaging and Release

- `tools/build_zips.py` builds `dist/metacognition-<version>.zip` with `metacognition/` as the single top-level entry, and refuses on a version mismatch, an upload-constraint violation, sync drift, or a top-level `bin/` (Component H).

#### G8: Docs Site and README

A mkdocs-material site in `docs/`, deployed to GitHub Pages, in the same shape as Mason's `markwright` docs (teal light and dark palette, mermaid fences, admonitions).
Pages:

- Home: what it does, who it is for, the credit line.
- Getting Started: install on Claude Code (marketplace), on claude.ai and Cowork (marketplace or the release zip through Customize, Plugins), and running the whole pipeline in one claude.ai conversation or a Project.
- The Five Stages: one page per stage with what it asks of the person, what it produces, roughly how long it takes, and what done looks like.
- Configuration: the tiers, the two keys, and the claude.ai options (state settings in the first message, or put them in Project instructions).

#### G9: Live Surface Check

Before the first release the maintainer runs a manual check on each surface and records the result in `docs/` or the session notes:

- No PyPI package for the scripts.
- No analytics or tracking on the docs site.
- No hooks, no MCP servers, and no HTML server in the plugin.
- The plugin never auto-chains stages and never auto-runs a calibration round.
- Skillify never bumps a version and never edits a plugin or marketplace manifest in the target.
- No required setup: no config file, account, or environment variable is ever needed to run a stage.

## Component boundaries

**Component A, the repo layout.**

```
.claude-plugin/marketplace.json
metacognition/                    the installable plugin
  .claude-plugin/plugin.json
  agents/domain-research.md
  skills/<stage>/SKILL.md         hand-authored
  skills/<stage>/references/      synced from src/references/
  skills/<stage>/scripts/         synced from src/scripts/
src/references/                   settings, extraction-theory, interview-spec-format, archive-format,
                                  profile-format, calibration-protocol, skill-scaffold, research-contract
src/scripts/                      yaml_subset.py, validate_artifacts.py, resolve_config.py, archive_append.py,
                                  update_token_estimate.py
tools/                            sync_skills.py, build_zips.py, prose_scrub.py
tests/                            pytest suites and fixtures/
evals/                            README.md and <stage>/evals.json
docs/, mkdocs.yml                 the docs site
```

**Component B, `tools/sync_skills.py`.**
Input: `src/` and the hand-declared manifest (G2's table).
Output: each skill's `references/` and `scripts/` hold exactly its manifest slice, byte-identical to `src/`; files not in the slice are removed.
`--check` exits non-zero and lists every missing, extra, or differing file, writing nothing.
`tests/test_sync_drift.py` fails when any copy differs from `src/`.
`tests/test_sync_manifest.py` fails when a SKILL.md names a `references/` or `scripts/` file its slice does not ship, and when a slice ships a file its SKILL.md never names.

**Component C, `src/scripts/yaml_subset.py`.**
Input: frontmatter text or a whole config file.
Output: a `dict`, or a raised error naming the line.
The subset: `key: value` pairs; strings bare or quoted; integers; bare ISO dates (`YYYY-MM-DD`), which parse to `datetime.date` as PyYAML reads them; `true`, `false`, and `null`; inline lists `[a, b]`; inline maps `{k: v}`, nested as the archive's `categories` field needs; block maps by indentation; `#` comments.
Anything else (anchors, tags, multi-document streams, block scalars beyond what the formats use) is an error, never a guess.
A parity test parses every fixture frontmatter with both `yaml_subset` and PyYAML and requires equal results; the `bad-yaml` fixture must fail in both.
If a ported fixture or format uses a construct outside this list, the parser grows to cover it and the list here is updated in the same change.

**Component D, settings and `src/scripts/resolve_config.py`.**
Two keys:

- `extractions_root`: where extraction directories live. Default `extractions`. A relative value resolves against the working directory; `~` expands.
- `exemplar`: path to a skill (its directory or its SKILL.md) whose shape skillify should match. Default none. Relative values resolve against the working directory.

Five tiers, highest first, merged key by key:

```
1. run-time      --set key=value (a skill passes its --extractions-root flag and any setting
                 the person stated in the conversation or in Project instructions this way)
2. project       ./.claude/metacognition.local.md        YAML frontmatter; body ignored
3. user-claude   ~/.claude/metacognition.local.md        YAML frontmatter; body ignored
4. user-xdg      $XDG_CONFIG_HOME/metacognition/config.yaml, default ~/.config/metacognition/config.yaml
5. default
```

The project file is looked up in the working directory only, with no upward search.
Decision (confirmed at review 2026-10-01): when both user files set a key, `~/.claude/` wins over XDG. Each config file actually read prints `Loaded config from: <path>` on stderr, so stdout stays pure JSON.
Output: JSON on stdout, one object per key with `value` (absolute path or null), `source` (the tier name), and for `exemplar` an `exists` boolean.
Exit 0 on success; exit 2 with one line naming the file and key on an unknown key, a wrong type, or an unparseable file; a missing file at any tier is skipped silently.
A configured `exemplar` that does not exist is not an error here: skillify skips the exemplar read silently and continues on the baseline and the scaffold (goal R12).
`src/references/settings.md` documents the same tiers, keys, and defaults for the skill to apply by hand when the script cannot run; on claude.ai that means tier 1 and the defaults.

**Component E, `src/scripts/validate_artifacts.py`.**
Input: one extraction directory.
Output: exit 0 when clean; non-zero with a findings list otherwise.
Checks, unchanged from private `main`: directory missing, directory empty, frontmatter parse, archive question numbering, archive category counts, profile token ceiling (10,000, raised from 5,000 by issue #3 after a four-register profile could not fit without cutting lines that passed the keep/cut test), token estimate mismatch, missing profile section, profile section order, incomplete golden example, calibration round contiguity.
The archive category count is a count of probes (goal R4): each `### Qnn [<category>]` heading counts one, except a battery, which counts the number in its `[items: n]` tag.
One check added by the interview retro phase, `archive-battery-items`: a heading with `[probe: battery]` carries `[items: n]` with n from 3 to 6, and its body holds exactly n numbered items under `**Q:**` and n numbered answers under `**A:**`; an `[items: n]` tag on any other probe type is also a finding.
The optional `## Open research` and `## Exports` sections are accepted when present and never required; the validator checks only that their line IDs (`R01`, `E01`) run contiguously.
An archive with no battery and neither optional section validates exactly as before.
It owns structure only; prose belongs to `tools/prose_scrub.py`.
`tests/test_validate_artifacts.py` is the private suite ported, plus the cases this phase adds: pass on `woodworking` and `woodworking-battery`, fail on each `extractions-bad` case with the expected finding.

**The archive format after the interview retro phase** (`src/references/archive-format.md` is the full statement; this is the contract the validator and the append script share).

```markdown
## Contradiction ledger
- L01 (Q07 vs Q23): "<claim A>" vs "<claim B>". Resolution: <...>

## Open research
- R01 (Q73): <what the person deferred to>. Status: unresolved | resolved in Q74

## Exports
- E01 (Q92): <topic> -> <destination skill or unassigned>

## Questions
### Q46 [<category>] [<register>] [probe: ladder]
**Q:** <question>
**A:** <verbatim answer>

### Q47 [<category>] [<register>] [probe: battery] [items: 3]
**Q:** <stem>
1. <item>
2. <item>
3. <item>
**A:**
1. <verbatim answer>
2. <verbatim answer>
3. <verbatim answer>

### Q74 [<category>] [<register>] [probe: evidence]
**Q:** <bottom lines with source links, and the ratification question>
**A:** <verbatim reaction>
```

Probe types: `forced-choice`, `ladder`, `contrast`, `artifact`, `critical-incident`, `triad`, `battery`, `evidence`.
Every entry other than a battery keeps the two-line body.

**Component F, the five skills and their port rules.**
Each skill declares its inputs and outputs by path and keeps its private procedure.
The port rules, applied to every skill, reference, fixture, and eval:

1. Frontmatter becomes the four allowed fields. Arguments move from `argument-hint` into an Arguments section in the body.
2. Remove the working-directory guard, the frontier-model paragraph, and every `model:` and `disable-model-invocation:` line.
3. "Mason" becomes "the person" (or "you" where the skill addresses them). The profile's fixed `priority` text ends "preserve the person's deeper judgment over surface style."
4. Paths become skill-relative; scripts run as `python3 scripts/<name>.py`.
5. Remove every private reference (the public `plugin-dev` plugin that goal R12 names is not one): other private plugins and skills, the private spec and its component letters, the vault, the dictation product name, BPE, and the `<CLAUDE_HELP>` tag. Where a skill told Claude to flag uncertainty with that tag, it now lists every uncertainty at the end of the task under "Open questions".
6. Each stage starts by resolving settings (Component D) and states the extraction root it will use in one line.
7. The extraction README status table drops the sync column.
8. Slug handling is unchanged: design derives and prints the slug; interview, compile, and calibrate default to the only extraction under the root and name the candidates when there are several; skillify requires an explicit slug.
9. Each stage ends by naming the files it wrote and the next stage's command, and stops.
10. The interview's dictation note is generic: speaking answers works well, and answers are kept as given apart from dash and quote normalization.

Skillify changes beyond those rules:

- The exemplar is the `exemplar` setting, an advanced option most people will not set. Without one, or with one that does not exist, the read is skipped silently and `references/skill-scaffold.md` is the only template; the scaffold's templates are complete on their own and name no private skill. Precedence is the person's decision, the provider baseline review, the exemplar, then the bundled templates (goal R12).
- Output target: `--into <dir>` writes the new skill under that directory as today. Without `--into` and without a `target_skill`, skillify writes `<root>/<slug>/skill/<slug>/` and packages `<root>/<slug>/skill/<slug>.zip` with `<slug>/` as its single top-level entry, ready to upload. Before packaging it tells the person the package contains the verbatim interview archive.
- A produced SKILL.md meets the same upload constraints as this plugin's own skills and uses skill-relative paths (its archive lookup is `grep -n "^### Q" references/archive.md`).
- `target_skill` accepts a directory path or `<plugin>:<skill>`, the latter resolving to `<working directory>/<plugin>/skills/<skill>/`. `--replace` and `--dry-run` behave as on private `main`. Augment first runs the structural assessment of goal R12 and presents keep-or-restructure when the structure is challenged; its diff path is otherwise as on private `main`.
- Versions: skillify stamps a `version:` on a new skill only when the target's neighbors carry one, in the neighbors' scheme, and reports what the person may want to bump. It names no version scheme of its own.
- Loader: on Claude Code, skillify may offer a `~/.claude/rules/<slug>.md` pointer so the skill loads for matching files, and writes it only on approval. On other surfaces the step is skipped.

**Component G, `metacognition/agents/domain-research.md`.**
Two request shapes.
Domain survey (design): input is a domain sentence, the consumer capability, and optional artifact paths; output is the fixed four-block shape (dimensions, schools, vocabulary, artifact types) or the `no relevant results` line.
Practice lookup (interview, goal R2): input is one question about practice in the domain and the person's stated lean; output is up to five bottom lines, each one sentence with a source link, or the `no relevant results` line.
Read-only tools; never dispatches.
The contract text equals `src/references/research-contract.md`, held by a test.

**Component H, `tools/build_zips.py` and the version and upload guards.**
Input: `marketplace.json`, the plugin tree.
Output: `dist/metacognition-<version>.zip`.
Refuses, with the offending file named, when: any SKILL.md, `plugin.json`, or `marketplace.json` version differs; a `description` exceeds 1,024 characters or contains an angle-bracket token; a `compatibility` exceeds 500 characters; a SKILL.md has a frontmatter key outside the allowed four; `sync_skills.py --check` reports drift; the plugin has a top-level `bin/`.
The zip excludes caches, `.DS_Store`, and anything outside `metacognition/`.
`tests/test_skill_versions.py` pins presence, version shape (SemVer during beta, CalVer at 1.0), and uniformity; `tests/test_build_zips.py` covers each refusal with a constructed bad tree.

**Component I, `tests/test_doctrine_invariants.py`.**
A grep-style guard over `metacognition/`, `src/`, `evals/`, `tests/fixtures/`, and `docs/`: none of the private tokens appear (`Mason`, `Arcadia`, `claude-code-plugin-private`, `CLAUDE_PLUGIN_ROOT`, `CLAUDE_HELP`, `Fable`, `Wispr`, `content-design`, `vault-routing`, `Hassid`), no SKILL.md or agent carries `model:` or `disable-model-invocation:`, and no skill body contains `../`.
The README, LICENSE, manifests, and this spec are outside its scope, since they carry the author name and the credit line by design.

**Component J, the docs site.**
Input: `docs/*.md` and `mkdocs.yml`.
Output: a site that `mkdocs build --strict` builds with no warnings, deployed by CI to GitHub Pages.
The Method and File Formats pages are written from `src/references/` and say the same thing; when a reference changes, its page changes in the same pull request.
Enabling Pages on the repository is a one-time manual step for the maintainer.

**Component K, `src/scripts/archive_append.py`.**
Input: one extraction directory and one entry: `--category`, `--register`, `--probe`, the question and the answer (each given inline or as a UTF-8 file, `--question-file` and `--answer-file`), and for a battery `--items n` with the items and answers as numbered lines.
Optional: `--saturated` to flip the category's flag, `--ledger <line>`, `--export <line>`, and `--research <line>` to append one line to that section with the next ID, and `--closing` to log a closing question under the `[closing]` pseudo-category, which touches no category tally.
Effect, in one run: assigns the next `Qnn`; appends the entry under `## Questions`; raises `questions_asked` by one and the category's `asked` by the entry's probe count; creates an optional section the first time a line is added to it; rewrites the README's `interview n/floor` cell.
It applies the one capture normalization (dash and curly-quote codepoints) to the question and the answer and changes nothing else in them.
It writes each file to a temporary name and renames it, archive first, so an interruption never leaves a half-written file.
Output: the assigned `Qnn` on stdout. Exit 0 on success; exit 2 with one line naming the problem on a missing or unparseable archive, a category not in the frontmatter, an `--items` value outside 3 to 6 or disagreeing with the numbered lines, or `--items` without `--probe battery`; on any error nothing is written.
An archive the script has appended to passes `validate_artifacts.py`; a test holds the two together.
Standard library only, built on `yaml_subset`, test-first.

**Component L, `src/scripts/update_token_estimate.py`.**
Input: one or more `profile.md` paths as positional arguments, and optionally `-c` or `--check`.
The estimate is the validator's own: everything after the closing frontmatter delimiter, counted in characters and divided by four. One function computes it, and the validator and this script both call that function.
Default mode: for each path, when the stored `token_estimate` differs from the recount, rewrite that one frontmatter line in place and report the old and new values; when it matches, report that it is current.
`--check`: report each stale profile and write nothing.
The frontmatter is handled by delimiter split and line prefix, the validator's mechanic: no regular-expression parsing and no YAML round trip, so no other byte of the file changes. The replacement stops at the closing delimiter, because `token_estimate` can appear in the body as prose.
Each path is handled independently, and a rewrite goes through a temporary file and a rename.
Exit codes: 0 when every profile is current or was updated; 1 when `--check` found a stale one; 2 when any path is missing or malformed (no frontmatter, no closing delimiter, or no `token_estimate` line), with one line naming the file and the problem. Exit 2 outranks exit 1.
Tests call `main(argv)` in process and cover the estimate arithmetic, the frontmatter-only replacement, and all three exit codes.
Standard library only, test-first.

## Success criteria

- Every recommendation in the retro maps to a goal R1 to R9, and each goal's text is present in the skill, reference, or script it names.
- `archive_append.py` followed by `validate_artifacts.py` exits 0 for an open probe, a battery, an evidence entry, a closing question, and each optional section line; each documented error exits 2 and leaves both files byte-identical.
- `validate_artifacts.py` exits 0 on `woodworking-battery`, exits non-zero with `archive-battery-items` only on `battery-item-mismatch`, and gives the same result as before on every fixture that existed before this phase.
